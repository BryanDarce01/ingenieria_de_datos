# 1. El Plan de ejecución en Spark

Cuando escribimos código Spark (DataFrame / SQL / Dataset), Spark **no ejecuta inmediatamente**. 

Primero construye una **representación interna del cómputo.**

###  Spark lo convierte en:

- Logical Plan

- Optimized Logical Plan

- Physical Plan


## 1.1 Logical Plan

Es un árbol de operadores lógicos (DAG lógico).

``` sql

SELECT country, COUNT(*)
FROM events
WHERE event_date = '2025-01-01'
GROUP BY country

```

Logical plan (simplificado):

``` scss

Aggregate [country], [count(1)]
  Filter (event_date = '2025-01-01')
    Relation [events]

```

Características:

- Describe **qué operaciones** se requieren

- No incluye detalles físicos

- No habla de particiones, CPUs, ni memoria

- Es declarativo.

- No tiene detalles físicos.

- No sabe en qué nodo se ejecutará.

- No sabe si usará hash join o sort merge.

- Solo describe ***qué queremos***.

Se puede ver con:

``` python

  df.explain(True)

```

## 1.2 Optimized Logical Plan

Catalyst aplica **reglas de optimización:**

Principales optimizaciones:

- **Predicate pushdown**

- **Projection pruning**

- Constant folding

- Reordenamiento de joins

- Eliminación de operaciones redundantes

Ejemplo:

- Quita columnas no usadas

- Empuja filtros lo más cerca posible de la fuente

Sigue siendo **lógico, no físico.**

## 1.3 Physical Plan

Spark selecciona **estrategias físicas** concretas.

Decisiones técnicas:

- Tipo de join:

    - BroadcastHashJoin

    - SortMergeJoin

- Número de stages

- Cuándo hacer shuffle

- Operadores físicos (HashAggregate, SortAggregate)

``` scss 

*(2) HashAggregate(keys=[country], functions=[count(1)])
+- *(2) Project [country]
   +- *(2) Filter (event_date = '2025-01-01')
      +- *(2) FileScan parquet events

```

Aquí ya aparecen:

- Operadores físicos

- Indicadores de ejecución (*)

- Lectura real del storage
