# Normalized and Denormalized

Son dos formas distintas de organizar la información. Cada una tiene ventajas y desventajas dependiendo del caso de uso (analítico, transaccional, velocidad de consulta, integridad, etc.).

# Normalized (Normalizado)

**Normalizar** es **dividir los datos en varias tablas relacionadas** para evitar duplicidad y mantener la integridad.

## Características

- Mínima redundancia (no se repite información).

- La data se separa en entidades pequeñas: clientes, productos, transacciones, etc.

- Las tablas se relacionan por keys (PK–FK).

- Muy común en:

    - **Bases [OLTP](1.%20OLTP_and_OLAP.md)** (transaccionales).

    - Aplicaciones que requieren consistencia y escrituras rápidas.

    - Modelos relacionales bien estructurados.

## Ejemplo normalizado

En vez de tener todo junto

Tabla Clientes:

| customer_id | nombre |
| ----------- | ------ |
| 1           | Ana    |


Tabla Pedidos:

| order_id | customer_id | fecha      |
| -------- | ----------- | ---------- |
| 100      | 1           | 2025-01-01 |


Tabla Productos:

| product_id | nombre |
| ---------- | ------ |
| 50         | Laptop |

Tabla Detalle de pedido:

| order_id | product_id | cantidad |
| -------- | ---------- | -------- |
| 100      | 50         | 1        |

- No hay duplicados.
- Todo se relaciona vía llaves.

# Denormalized (Desnormalizado)

**Desnormalizar** es **combinar** o **duplicar** datos para acelerar **lecturas** y simplificar consultas.

La redundancia es **intencional** para que el análisis sea más rápido.

## Características

- Más redundancia, más columnas, más duplicación.

- Ideal para:

    - **Data warehousing** [(OLAP)](1.%20OLTP_and_OLAP.md).

    - Modelos estrella (star schema).

    - Tablas wide (anchas) para BI.

- Optimizas **lecturas**, sacrificas integridad.

#### Ejemplo desnormalizado

Una tabla de "ventas" con toda la información:

| order_id | fecha      | customer_name | product_name | cantidad |
| -------- | ---------- | ------------- | ------------ | -------- |
| 100      | 2025-01-01 | Ana           | Laptop       | 1        |

- Más rápido para hacer dashboards.
- No necesitas muchos JOINs.
- ❌ Si Ana cambia de nombre, hay que actualizar muchas filas.

# ¿Cuándo usar cada uno?

| Caso                                                    | Recomendado  |
| ------------------------------------------------------- | ------------ |
| **APIs transaccionales / aplicaciones**                 | Normalized   |
| **Eventos que requieren consistencia**                  | Normalized   |
| **Analytics / BI / Snowflake / Redshift / BigQuery**    | Denormalized |
| **Modelos de datos tipo estrella (fact + dimensiones)** | Denormalized |
| **Performance de lectura > escritura**                  | Denormalized |
| **Performance de escritura > lectura**                  | Normalized   |


## Regla práctica

- **Normalized** → OLTP → Integridad

- **Denormalized** → OLAP → Velocidad en lectura
